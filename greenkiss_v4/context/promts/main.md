Если я не прикладываю код, значит для формирования промта он не нужен. Если код приложен, не переписывай его и не пересказывай, используй только как контекст.

### Общие правила формулировки промта

1. **Без противоречий**  
   - Не допускать конфликтующих требований, технологий, путей и паттернов.  
   - В случае неоднозначности — явно зафиксировать выбранный вариант в тексте промта.

2. **Без повторов**  
   - Не дублировать требования, стек и правила.  
   - Общие принципы описывать один раз, далее ссылаться на них.

3. **Без пустых формулировок**  
   - Не использовать общие фразы без конкретики:  
     «сделать качественно», «написать хороший код», «использовать лучшие практики» и т.п.  
   - Всегда уточнять конкретные требования: структура файлов, формат типов, формат ответов, ожидаемое поведение.

4. **Без `any`**  
   - В промте явно указывать запрет на использование типа `any`.  
   - Требовать строгую типизацию, использование типизированных утилит и дженериков, где это оправдано.

### Архитектура и организация кода

В каждом промте обязательно указывать:

1. **Принципы проектирования**
   - Следовать SRP (Single Responsibility Principle).  
   - Следовать low coupling, high cohesion.  
   - Все, что связано с одной сущностью/модулем, должно быть сгруппировано в одной папке:  
     - типы  
     - серверные экшены (server actions)  
     - UI-компоненты  
     - страницы  
     - API-обработчики  
     - вспомогательные функции, хуки и т.д.  

2. **Исключения для drizzle**
   - Все схемы drizzle хранить по пути:  
     `@/shared/api/db/schemas/`  
   - Одна схема — один файл.

3. **Структура модулей**
   - Внутри любого модуля/фичи в корне только два файла:
     - `index.ts` — реэкспорт всего клиентского/общего функционала из внутренних папок.
     - `server.ts` — реэкспорт только серверной логики/серверных экшенов.  
   - Остальное — только подпапки с префиксом `_`:
     - `_ui/` — компоненты интерфейса модуля  
     - `_lib/` — утилиты, вспомогательные функции, доменная логика модуля  
     - при необходимости: `_model/`, `_api/`, `_store/` и т.п.  
   - В промте явно описывать, какие файлы/части нужно создать внутри этих подпапок.

4. **Именование**
   - Требовать:
     - осмысленные, точные имена переменных, функций, компонентов, пропсов, файлов и папок;
     - соответствие имени доменной логике и назначению сущности;
     - отсутствие сокращений, если они не являются общепринятыми.  
   - Если в моих задачах используются плохо названные сущности, нужно:
     - в промте переформулировать их с правильными именами;
     - сохранить связь с исходным смыслом (чтобы было понятно, о чём речь).
   - Все файлы пишутся в стиле file-name.extantions
