Проектирование и реализация drizzle-схем для каталога интернет‑магазина (категории, бренды, атрибуты, товары, характеристики) с учётом производительности и вложенной структуры категорий.

---

2. **Контекст проекта (кратко)**

- Стек:  
  - Next.js 16.0.3  
  - drizzle ORM + postgres.js + PostgreSQL  
  - tailwindcss  
  - @aws-sdk/client-s3  
  - next-auth 5.0.0-beta.30  
  - zod  
  - zustand  

- Архитектурные правила:
  - Строгий SRP, low coupling, high cohesion.
  - Логика, относящаяся к одной доменной сущности/модулю, группируется в одной папке (типизация, server actions, UI, API‑обработчики, утилиты, сторы и т.д.).
  - Исключение для drizzle: все таблицы и enum’ы описываются в `@/shared/api/db/schemas/`, одна схема — один файл.
  - В модулях/фичах в корне только:
    - `index.ts` — реэкспорт клиентской/общей логики из подпапок.
    - `server.ts` — реэкспорт только серверной логики/server actions.
    - Вся остальная структура — подпапки с префиксом `_` (`_ui`, `_lib`, `_model`, `_api`, `_store` и т.п.).
  - Именование: осмысленные имена без неочевидных сокращений, соответствие доменной логике, файлы в стиле `file-name.ts`.
  - Все пользовательские тексты (UI, уведомления, пользовательские ошибки) — на русском.
  - Тексты для разработчиков (комментарии, `throw new Error`, логи) — на английском.
  - Компоненты shadcn-ui импортируются только из `@/shared/ui/kit/`.
  - В TypeScript запрещён `any`. Требуется строгая типизация, осмысленные типы и дженерики, если это оправдано.

- Текущие схемы пользователей уже расположены в `@/shared/api/db/schemas/users.ts` и подключены через `@/shared/api/db/index.ts`. Новые схемы нужно вписать в эту же архитектуру.

3. **Конкретные задачи для ИИ**

Твоя задача — спроектировать и реализовать drizzle-схемы PostgreSQL для каталога интернет‑магазина на основе описанного домена, а также явно описать варианты схем и их асимптотику (O-сложность) для основных операций. Писать только схемы и технические комментарии, без реализации UI/серверных экшенов.

**Общие требования к коду в этом промте:**

- Язык — TypeScript + `drizzle-orm/pg-core`.
- Не использовать `any`.
- Каждая схема — отдельный файл в `@/shared/api/db/schemas/`.
- Для id использовать тот же подход, что в `users` (например, `text().$defaultFn(() => createId())`), если это уместно, либо `serial`/`bigserial` при необходимости.
- Не добавлять аудиторские поля (`createdAt`, `updatedAt`, `createdBy`, и т.п.), если они не нужны для конкретной задачи.
- В коде и комментариях — английский язык; в названиях таблиц/полей допускается английский, доменно точный, без транслита.
- Не изменять уже существующие схемы пользователей, только дополнять общую схему новыми сущностями.

### 3.1. Схемы для категорий

**Задача:**

Спроектировать таблицу/таблицы для иерархических категорий, удовлетворя требованиям:

- Категории могут вкладываться друг в друга на любую глубину.
- URL категории строится по структуре:  
  - `parent-category/child-category/`  
  - или `parent-category/` (если у неё нет детей либо она единственная в иерархии).
- При переходе по категории сайт должен уметь отрисовать нужную страницу **без запросов к БД**:
  - Т.е. структура дерева категорий и их `slug`‑и должны быть доступны для SSG/ISR/статического роутинга.  
  - Явно опиши в комментариях, какие именно поля/структуру надо будет выгружать на билд/regen, и как это влияет на схему (например, хранить полный `path_slug` или нет).

**Требуемые поля категории:**

- `id`
- `name` — название категории
- `slug` — часть URL (уникальная в рамках одного родителя)
- `sortOrder` — числовое поле для ручной сортировки в админке
- `imageUrl` — опциональная ссылка на изображение в S3
- Поле(я) для связи с другими категориями для реализации иерархии:
  - Обязательно реализовать один из вариантов:
    1. Простая adjacency list (поле `parentId`).
    2. Nested set.
    3. Materialized path.
    4. Другое
  - Нужно описать плюсы и минусы, а также О сложность поиска, сортировки, фильтрации и CRUD операций каждого варианта.

**Требования к реализации:**

1. Создать файл схемы, например:  
   `@/shared/api/db/schemas/categories.ts`
2. Определить:
   - таблицу для категорий (например, `categories`),
   - необходимые индексы:
     - по `parentId` (если adjacency list),
     - по `slug` в связке с `parentId`,
     - по полю, обеспечивающему быстрый поиск категории по полному пути (если используется `fullSlugPath` или аналог).
3. В комментариях к схеме:
   - Описать, как строится URL категории.
   - Описать асимптотику основных операций:
     - поиск категории по полному пути (например, `parent/child/subchild`),
     - выбор всех дочерних категорий,
     - вставка новой категории (изменение/неизменение дерева),
     - обновление `slug`/перемещение категории в другое место дерева.
   - Оценить `O(...)` с учётом выбранного паттерна (adjacency list, materialized path и т.д.) и необходимых индексов в PostgreSQL.

### 3.2. Схемы для брендов

**Задача:**

Спроектировать таблицу для брендов, которые:

- Имеют:
  - `id`
  - `name` — уникальное имя бренда
  - `imageUrl` — опциональная ссылка на картинку в S3
- Должны:
  - Быстро искаться по названию при вводе пользователем (поиск и автокомплит для фильтрации).
  - Быть связаны с товарами (многие товары к одному бренду).
  - Выводиться в рамках категории только те, что привязанны к товарам этой категории (Как реализовать наилучшую О сложность, чтобы не пробегаться по всем твоарам чтобы вывести все бренды)

**Требования к реализации:**

1. Создать файл схемы, например:  
   `@/shared/api/db/schemas/brands.ts`
2. Определить таблицу брендов (например, `brands`) с:
   - уникальным индексом по `name`,
   - дополнительным индексом по `lower(name)` или отдельному полю для case-insensitive поиска (опиши выбранный подход),
   - опциональным полем `searchVector` (если предлагаешь использовать `tsvector`) либо явно откажись от этого варианта и опиши, почему.
3. В комментариях к схеме описать:
   - Асимптотику:
     - поиск бренда по точному имени,
     - поиск бренда по префиксу/like для автокомплита,
     - выбор брендов по `id` из списка (когда фильтруем товары).
   - Предлагаемые индексы и стратегию поиска (B-Tree по `name`, `GIN` по `tsvector` и т.п., если ты это предлагаешь).

### 3.3. Схемы для атрибутов и их значений

**Доменное описание:**

- Атрибут — это сущность вроде «размер», «цвет» и т.п.
- Для **каждого атрибута** может быть множество **значений атрибута** (например, цвет: «зелёный», «жёлтый», размер: «S», «M»).
- Требования:
  - В контексте страницы категории должны выводиться только те атрибуты/значения, которые реально присутствуют у товаров этой категории.
  - Для конкретного типа атрибутов («атрибут с фото», например, цвет) требуется:
    - у **каждого значения атрибута** своя картинка (`imageUrl`), которая определяет набор изображений товара (переключение картинок по цвету).
    - у значения атрибута есть **маленькая главная миниатюра** для отображения над выбором атрибутов (отдельное поле).
    - Также можно до 5 изображений добавить. Их можно в ручную сортировать в админке. Главное изображение дополнительно уменьшается и используется на странице поиска (нужно поле для ссылкин а s3 для него)
  - Если у атрибута/значения нет привязки к отдельным картинкам, все варианты считаются одним товаром на уровне карточки категории.

**Требования к структуре:**

- Отделить:
  - таблицу для типов атрибутов (например, `attributeTypes`),
  - таблицу для значений атрибутов (например, `attributeValues`).
- Поля для типа атрибута:
  - `id`
  - `name` — «Размер», «Цвет» и т.д.
  - флаг/enum, определяющий, является ли атрибут «с фото» (например, `hasImageVariants` boolean либо enum `attribute_kind`).
- Поля для значения атрибута:
  - `id`
  - `attributeTypeId` — связь с типом атрибута
  - `value` — конкретное значение (например, «зелёный», «XL»)
  - `imageUrl` — опциональная ссылка на основное изображение варианта (для «атрибутов с фото»)
  - `thumbnailUrl` — опциональная ссылка на «микро» изображение для отображения над кнопкой выбора варианта
  - при необходимости — поле сортировки для значений внутри одного атрибута (`sortOrder`)

**Требования к реализации:**

1. Создать два файла:
   - `@/shared/api/db/schemas/attribute-type.ts`
   - `@/shared/api/db/schemas/attribute-value.ts`
2. Определить индексы:
   - по `(attributeTypeId, value)` в `catalogAttributeValues` для уникальности и быстрых выборок.
3. В комментариях:
   - Указать, как эта модель позволит:
     - выбрать доступные атрибуты/значения для категории (через связь товары → категории и товары → значения атрибутов),
     - отделить «атрибуты с фото» от простых атрибутов.
   - Описать асимптотику:
     - выбор атрибутов для категории,
     - выбор значений атрибутов для набора товаров,
     - CRUD для типов и значений атрибутов.

### 3.4. Схемы для товаров, вариантов товара и картинок

**Доменное описание:**

- Товар:
  - Имеет общее:
    - `name`
    - `basePrice` (основная цена)
    - варианты скидки:
      - в процентах
      - в абсолютном значении
    - принадлежность к бренду
    - привязку к категориям
  - Может иметь различные комбинации атрибутов (варианты товара).
- Вариант товара:
  - У каждого варианта своё:
    - Количество (stock).
    - Набор картинок (до 5 штук), с возможностью ручной сортировки.
    - Для «атрибутов с фото» у каждого варианта свой набор картинок (цвет → свои фото).
- Картинки:
  - Ссылка на S3.
  - Позиция (сортировка).
  - Варианты размеров:
    - главное (для карточки товара в списке категории),
    - микро (для отображения над кнопкой выбора атрибута с фото).
  - Требуется чётко разделить:
    - «набор картинок варианта товара» (основные изображения),
    - «микро» / «мини» версия (или указать тип изображения через enum).

**Требуемая модель (предлагаемый подход, который надо реализовать и можно скорректировать/уточнить в комментариях):**

1. Таблица `catalogProducts`:
   - `id`
   - `name`
   - `brandId` (FK на бренд)
   - базовая цена: `basePrice` (numeric/decimal)
   - скидка:
     - `discountPercent` (numeric / smallint, nullable)
     - `discountFixed` (numeric, nullable)
     - В комментариях описать, как рассчитывается итоговая цена (какой приоритет, и допускается ли одновременное заполнение двух полей).
   - связь с категориями — **многие‑ко‑многим** через отдельную таблицу (см. ниже).
2. Таблица `catalogProductCategories` (связь товар ↔ категория):
   - `productId`
   - `categoryId`
   - составной первичный ключ или уникальный индекс.
3. Таблица `catalogProductVariants`:
   - `id`
   - `productId`
   - `stockQuantity` — количество на складе для конкретного набора атрибутов
   - необязательные поля для переопределения цены/скидок (если нужно поддержать разную цену по цвету/размеру) — явно укажи, используешь ты это или нет.
4. Таблица `catalogProductVariantAttributes`:
   - связь варианта товара с конкретными значениями атрибутов:
   - `variantId`
   - `attributeValueId` (FK на `catalogAttributeValues`)
   - позволяет моделировать комбинацию: цвет=зелёный, размер=XL и т.п.
5. Таблица `catalogProductVariantImages`:
   - `id`
   - `variantId`
   - `imageUrl` — ссылка на изображение в S3
   - `position` — порядок отображения (1..5)
   - флаги/enum:
     - либо два boolean: `isMain` (главное изображение), `isMicro` (микро-версия),
     - либо enum `imageKind` с вариантами (`"main" | "gallery" | "micro"`).
   - В комментариях зафиксировать, какой вариант ты выбираешь и как формируется:
     - «главное» изображение для списка товаров в категории,
     - «микро» изображение над кнопкой выбора атрибута (показывается только для «атрибутов с фото»).
   - Обозначить ограничение «до 5 фото на вариант» в виде бизнес-правила в комментариях (DB-constraint не обязателен, но можно описать варианты, как его реализовать).

**Требования к реализации:**

1. Создать схемы:
   - `@/shared/api/db/schemas/catalog-product.ts`
   - `@/shared/api/db/schemas/catalog-product-category.ts`
   - `@/shared/api/db/schemas/catalog-product-variant.ts`
   - `@/shared/api/db/schemas/catalog-product-variant-attribute.ts`
   - `@/shared/api/db/schemas/catalog-product-variant-image.ts`
2. Определить индексы:
   - по `brandId` в `catalogProducts`,
   - по `categoryId` и `productId` в таблице связки,
   - по `productId` в `catalogProductVariants`,
   - по `variantId` в таблицах атрибутов и изображений.
3. В комментариях:
   - Описать асимптотику:
     - выбор товаров по категории,
     - выбор брендов, доступных для товаров категории (через join по продуктам категории),
     - выбор атрибутов/их значений, доступных для товаров категории (через join по вариантам и значениям атрибутов),
     - выбор картинок для конкретного варианта.
   - Предложить варианты оптимизации для:
     - быстрого получения списка брендов по категории (например, индекс/материализованный view/денормализация через кэширующую таблицу) и оценить торговые‑offs.
     - быстрого получения доступных атрибутов для категории (аналогично).

### 3.5. Схемы для характеристик товара (не выбора варианта)

**Доменное описание:**

- Характеристика товара — это информационное свойство, участвующее в фильтрации, но не определяющее вариант:
  - Примеры: «Состав», «Материал», «Сезон».
  - Состоят из пары: название характеристики + значение.
  - Могут повторяться между товарами (например, «Материал: хлопок» у множества товаров).
- Требуется:
  - Уметь фильтровать товары по характеристикам.
  - Возможность переиспользования одинаковых названий/значений (чтобы не дублировать строки без нужды, если это выгодно).

**Требуемая модель (предложение, можно уточнить в комментариях):**

- Таблица `catalogPropertyTypes`:
  - `id`
  - `name` — «Материал», «Сезон» и т.п.
- Таблица `catalogPropertyValues`:
  - `id`
  - `propertyTypeId`
  - `value` — «хлопок», «лето» и т.п.
- Таблица `catalogProductProperties` (связка товара и значения свойства):
  - `productId`
  - `propertyValueId`
  - составной PK или unique.

**Требования к реализации:**

1. Создать файлы:
   - `@/shared/api/db/schemas/catalog-property-type.ts`
   - `@/shared/api/db/schemas/catalog-property-value.ts`
   - `@/shared/api/db/schemas/catalog-product-property.ts`
2. В комментариях:
   - Объяснить, как эта модель будет использоваться для фильтрации товаров по характеристикам.
   - Описать асимптотику:
     - выбор доступных характеристик для категории,
     - фильтрация товаров по заданным характеристикам (например, «Материал: хлопок», «Сезон: зима»),
     - CRUD-операции по типам и значениям характеристик.
