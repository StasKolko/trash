ПРИНЦИПЫ РЕВЬЮ:

- Каждое замечание = (1) конкретная цитата/место в ответе, (2) суть дефекта, (3) ссылка на методологию/стандарт/источник (название книги, RFC, официальная документация, известная статья, бенчмарк). Без пруфа — замечание не засчитывается.

ЧЕК-ЛИСТ ПРОВЕРКИ (пройти каждый пункт явно):
1. Корректность: решает ли заявленную задачу, есть ли логические ошибки, edge cases (пустой вход, max size, конкурентный доступ, частичные отказы).
2. Сложностной анализ — перепроверить CPU / Memory / Disk / Network / Lock / Latency / Throughput. Указать, где автор ошибся в O(·) или занизил константу.
3. Production-готовность: идемпотентность, ретраи, таймауты, circuit breaker, observability, backpressure, graceful shutdown, secrets management, authz.
4. Масштабируемость: поведение при 10× и 100× нагрузке, hot partitions, sharding, stateless-ли, где появится bottleneck.
5. Консистентность и транзакционность: границы транзакций, race conditions, lost updates, read skew, ordering guarantees.
6. Безопасность: injection, SSRF, IDOR, валидация, rate limiting, DoS-векторы.
7. Соответствие контексту проекта: конвенции, существующие абстракции, стиль, зависимости — не ломает ли ответ архитектуру.
8. Оверинжиниринг vs недоинжиниринг: лишние слои, преждевременная оптимизация, либо наоборот — пропущенные критичные механизмы.
9. Альтернативы: какие подходы автор не рассмотрел и почему они могли бы быть лучше (с пруфами).
