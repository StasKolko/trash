# Рефакторинг

## Шкала оценки

**0-10**, где **9** = production-ready код, не требующий изменений.

---

## Принципы программирования

### Фундаментальные

| Принцип | Применение |
|---------|------------|
| **SRP** (Single Responsibility) | Один файл/функция = одна задача. Функция > 40 строк → разбить. Файл > 250 строк → пересмотреть |
| **DRY** (Don't Repeat Yourself) | Дублирование > 2 раз → выносить |
| **KISS** (Keep It Simple) | Минимум абстракций, максимум читаемости |
| **YAGNI** (You Aren't Gonna Need It) | Не писать код "на будущее" |
| **Composition over Inheritance** | Композиция функций вместо наследования |
| **Immutability** | Не мутировать входные данные |

---

### Fail Fast

| Ситуация | Действие | Пример |
|----------|----------|--------|
| **Критичная ошибка** — продолжение невозможно, приложение не может работать | `throw new Error` | Невалидный env при старте, нарушена целостность конфигурации |
| **Все остальные случаи** — ошибка обрабатываема | `Result<T>` через `ok`/`fail` | Сетевые запросы, валидация данных, browser API, файловые операции |

| Принцип |
|---------|
| Следовать официальным паттернам: сигналы, stores, createMemo, createEffect. Документация: solidjs.com/docs |

## Типизация

| Правило | Пример |
|---------|--------|
| **Инлайн типы по умолчанию.** Выносить только при экспорте в другой файл | `function Button(props: { label: string })` |
| **Общие типы в начало файла** — если используется >1 раза в ОДНОМ файле | `type MaybeElement = Element \| null \| undefined` |
| Не указывать return type функций — TS выводит сам | — |
| **`interface` запрещён** — только `type` | — |
| **`any` запрещён** — использовать `unknown` + type guard | — |
| **`as` запрещён** — если требуется `as`, значит нужно исправить код или типизацию | — |
| Валидация runtime данных через typebox на backend или valibot на frontend | — |
| **Без `ComponentProps`** — явно указывать только нужные props. Жёсткая дизайн-система снимает когнитивную нагрузку с разработчика | — |

## Async/Await

| Правило | Пример |
|---------|--------|
| **Использовать Result API** (`tryCatch`, `tryCatchAsync`) для всех операций, которые могут упасть | — |
| **throw только для невосстановимых ошибок** — валидация env при старте, критичные инварианты | — |
| **Не игнорировать Promise** — всегда await или void для fire-and-forget | `void analytics.track()` |

## Именование

| Правило | ❌ Плохо | ✅ Хорошо |
|---------|----------|-----------|
| Пакеты/модули: `frontend`/`backend` | `browser`, `server` | `frontend`, `backend` |
| Runtime проверки: `isServer` из `solid-js/web` | — | `if (isServer) { return }` |

---

## Синтаксис

| Правило | ❌ Плохо | ✅ Хорошо |
|---------|----------|-----------|
| Блоки всегда в `{}` | `if (x) return` | `if (x) { return }` |
| Без тернарных операторов в runtime коде. **Операторы `??`, `\|\|`, `&&` — можно.** В типах тернарные разрешены (conditional types) | `x ? a : b` | `if (x) { return a } return b` или `x && doSomething()` |
| Закон Де Моргана | `!a \|\| !b` | `!(a && b)` |
| Позитивные условия в основной логике | `if (!valid) { doWork() }` | `if (valid) { return } doWork()` |
| **Early return с отрицанием — ОК** | — | `if (!isValid) { return }` |

**Приоритет правил 24-25:** Early return (25) важнее позитивных условий (24). Сначала отсекаем невалидные случаи, потом пишем основную логику позитивно.

## SSR/SPA совместимость

| Проблема | Решение |
|----------|---------|
| `window`, `document`, `navigator` и другие browser API | Только через `isServer`|
| `setTimeout`, `setInterval` в top-level | Обернуть в `createEffect` или `onMount` |
| Рандомные ID при гидратации | `createUniqueId()` из SolidJS |
| Разный контент server/client | Проверка `isServer` + условный рендеринг |

## Тестирование

| Правило |
|---------|
| **Unit-тесты обязательны** для: утилиты, хелперы, чистые функции, ui компоненты из packages |
| **Оптимизация:** Убирать дубликаты тестов. Оптимизировать сами тесты по памяти и времени. Объединять несколько проверок в одну во время циклов. |
| **Именование:** `*.test.ts` рядом с файлом |
| **Синтаксис:** Используем только `it` (не `test`). После `it` всегда идёт `should`: `it('should return empty array', ...)` |
| **Структура AAA:** Arrange (подготовка) → Act (действие) → Assert (проверка). Разделять пустой строкой. |
| **Комментарии:** Запрещены, кроме `biome-ignore` |
| **DRY в тестах:** Переиспользуемые хелперы → `@packages/testing`. Локальные дубликаты → в начало файла. |

## Form Controls

| Правило |
|---------|
| **Без `class` prop** — дизайн-система не принимает внешние классы, позиционирование через родителя. **Исключение:** компоненты, которым часто нужно абсолютное позиционирование (например, Badge) |
| **`id` и `name`** — для связи с `<label for="">` и FormData |
| **`disabled`** — у всех контролов |
| **`readonly`** — у всех контролов |
| **`required` только для контролов с валидацией** |
| **`open/checked` + `onOpenChange/onCheckedChange` везде** |
| **`invalid` + `invalidMessage` + `invalidId`** — для состояния ошибки (не `error`, чтобы не путать с Error объектом) |
| **Классы выносить в `const classes`** — отделение стилей от логики, в начало файла. Формировать через `[].join(" ")` для читаемости |

```typescript
const classes = [
  "inline-flex",
  "items-center",
  "rounded-md",
  "border",
].join(" "),
```

## Компоненты

| Правило |
|---------|
| **Без хардкод текста** — весь текст через props для i18n |
| **`aria-label` обязателен** (в props может быть опционален) там, где визуальный текст может быть недостаточен для screen readers (например, Badge с числом, иконки) |
| **`data-testid` у всех компонентов** — сразу указываем как название компонента |
| **Border обязателен** у всех интерактивных элементов. Для "невидимого" border → `border-color: transparent` или цвет background. Это позволяет легко добавить/убрать видимую границу изменением одного токена |
| **aria-hidden="true"** у всех элементов внутри элемнта с `aria-label`, а также для иконок и непонятного тектса, например: 20 / 300 |
