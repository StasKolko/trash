

## Итоговая формулировка: Admin Permissions — Grant система

---

### Концепция

**Permission = право на действие.** Например `users.view`, `system_logs.delete`.

**Grant = право выдавать/отзывать permissions другим.** Например `users.grant` — право управлять пермишенами в рамках сущности `users`.

---

### Что даёт `{entity}.grant`

Имея `users.grant`, ты можешь выдавать и отзывать **только те `users.*` пермишены, которые есть у тебя самого**, исключая сам `users.grant`.

**Пример:** У админа есть `users.view`, `users.manage`, `users.grant`.
- ✅ Может выдать `users.view` — есть у него
- ✅ Может выдать `users.manage` — есть у него
- ❌ Не может выдать `users.export` — нет у него
- ❌ Не может выдать `users.grant` — grant не передаётся
- ❌ Не может выдать `system_logs.view` — другая сущность, нужен `system_logs.grant`

---

### Кто может выдавать `.grant` пермишены

**Только owner.** Никто другой не может выдать `*.grant` пермишен. Это защита от каскадного распространения прав.

---

### Кому можно выдавать/отзывать

| Действие | Целевая роль: строго ниже | Целевая роль: такая же | Целевая роль: выше |
|----------|---------------------------|------------------------|--------------------|
| Выдать | ✅ Свои пермишены (без `.grant`) | ✅ Свои пермишены (без `.grant`) | ❌ |
| Отозвать | ✅ Свои пермишены (без `.grant`) | ❌ | ❌ |

- Нельзя менять свои собственные пермишены
- Нельзя менять пермишены owner
- Нельзя менять пермишены пользователей с ролью `user` (у них `adminPermissions = null`)

---

### Страница Permissions в админке

**Доступ:** Все, кто попал в админку (moderator+).

**Что видишь:**

| Состояние | Что отображается |
|-----------|-----------------|
| Нет ни одного `*.grant` | Только себя и свои пермишены (readonly) |
| Есть хотя бы один `*.grant` | Себя + всех пользователей своей роли и ниже (кроме `user`) |

**Фильтрация на сервере.** API endpoint для страницы Permissions возвращает:
- Если нет `*.grant` → только запрашивающего пользователя
- Если есть `*.grant` → пользователей с ролями: своя роль + строго ниже, исключая `user`

**Пользователи с ролью `user` НИКОГДА не отображаются** на странице Permissions. Им нельзя выдать админ-пермишены, у них `adminPermissions = null`.

---

### Пример полной цепочки

**Owner** выдаёт admin'у: `users.view`, `users.manage`, `users.grant`, `system_logs.view`.

**Admin** теперь может:
- Видеть на странице Permissions: себя, других admin'ов, всех moderator'ов
- Выдать moderator'у `users.view` ✅ (есть у него + есть `users.grant`)
- Выдать moderator'у `users.manage` ✅ (есть у него + есть `users.grant`)
- Отозвать у moderator'а `users.view` ✅ (строго ниже по роли)
- Выдать другому admin'у `users.view` ✅ (та же роль, выдача разрешена)
- Отозвать у другого admin'а `users.view` ❌ (та же роль, отзыв запрещён)
- Выдать кому-либо `users.grant` ❌ (grant не передаётся)
- Выдать кому-либо `users.export` ❌ (нет у него самого)
- Выдать кому-либо `system_logs.view` ❌ (нет `system_logs.grant`)
- Выдать кому-либо `system_logs.delete` ❌ (нет `system_logs.grant`)

---

### Нюансы

1. **Grant привязан к сущности.** `users.grant` даёт управление только `users.*`. Для `system_logs.*` нужен `system_logs.grant`. Для `admin_audit_logs.*` нужен `admin_audit_logs.grant`.

2. **Grant не даёт grant.** Даже имея `users.grant`, ты не можешь выдать кому-то `users.grant`. Только owner.

3. **Owner обходит всё.** Owner не проверяет пермишены вообще. Может выдать/отозвать любой пермишен любому (кроме другого owner, но owner один).

4. **API endpoint для grant — один.** `PATCH /v1/users/:id/permissions` принимает полный массив пермишенов. Сервис вычисляет diff (added/removed) и проверяет каждый пермишен по правилам выше.

5. **Доступ к endpoint.** Endpoint permissions доступен если у пользователя есть **хотя бы один `*.grant`** пермишен. Owner доступ автоматический.
