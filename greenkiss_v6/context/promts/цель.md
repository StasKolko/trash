ПРОФЕССИОНАЛЬНЫЙ ПРОМПТ ДЛЯ ПРОГРАММНОГО АРХИТЕКТОРА: Green Kiss (greenkiss.ru)

Контекст и цель
- Проект: разработка высокопроизводительного интернет-магазина Green Kiss.
- Домен: greenkiss.ru
- Технологии: Next.js 16.0.3 (RSC, App Router, Server Actions), Postgres + postgres.js, Drizzle ORM, S3-совместимое хранилище для изображений/CDN.
- Текущие сущности аутентификации (NextAuth) уже есть: users, accounts, sessions, verificationTokens, authenticators, userRoleEnum (USER, ADMIN, MANAGER).
- Цель: спроектировать архитектуру данных, API, доступы и интерфейсы с гарантированно низкими сложностями операций (поиск, сортировка, фильтрация, CRUD), высокой скоростью ответов и масштабируемостью.

Обязательные требования к данным и связям
1) Категории (любой уровень вложенности):
   - Поля: name (RU), slug (транслитерация “Женщинам → zhenshchinam”), full_path, parent_id, статус (draft|active|hidden), sort_order (для ручного меню), level, created_at/updated_at.
   - SEO: meta_title (по умолчанию name), meta_description, og_title (по умолчанию name), og_description, og_type (обычно website), meta_robots (по умолчанию index,follow), canonical_url (домен + full_path).
   - Изображения: для соцсетей категории по умолчанию используют глобальный логотип/картинку сайта из отдельной сущности SiteAsset. Возможность переопределения опциональна и должна быть аргументирована.
   - Дерево: использовать CategoryClosure (ancestor_id, descendant_id, depth) с индексами по ancestor_id/descendant_id. Требования: O(log N) или O(1) по числу уровней для хлебных крошек, выборки поддеревьев и агрегаций.

2) Бренды:
   - Поля: name (любой язык), optional image (например, 32×32 webp), created_at/updated_at.
   - Связь с категориями: не прямое редактируемое множество, а материализованная таблица brand_category, которую поддерживаем автоматически от товаров: когда товар получает/теряет категории — пересчитывается связь бренда с соответствующими категориями и их предками. Требования: обеспечить уникальность и корректность удаления/добавления с правильной сложностью. Нужен алгоритм, исключающий лишние удаления у родителя, если остаются другие товары бренда. Важно помнить, что бренд может начать производить товар из другой категории, поэтому на клиенте выбор бренда только прикрепленному к категории. А на админке выбор бренда прикрепленных и отдельно не прикрепленных. Имя бренда должно быть уникальным.
   - SEO для брендов не делаем.

3) Атрибуты/характеристики и фильтры:
   - Примеры: цвет, сезон, размер, материал и пр.
   - Привязка к категориям: атрибут назначается конкретной категории; действует для нее и может наследоваться родителям/потомкам — предложить четкие правила наследования и удаления. Пример: если “материал” задан у “Легинсы”, что происходит при удалении “Легинсы”? Нужно описать стратегию.
   - Типизация атрибутов: строка, перечисление, число, диапазон, булево, множественный выбор; нормализованные значения для индексации.
   - Обязательность: если для категории задан обязательный атрибут — любой товар в этой категории должен иметь валидное значение.
   - Связь с изображениями вариантов: если атрибут (например, цвет) имеет изображения (до 5 шт. на значение), то отображение товара на витрине дробится по значениям с изображениями (green куртка, red куртка), а не по размеру. Если изображения не заданы — показывается один товар. Нужна четкая модель вариантов и правила индексации/поиска по ним.
   - Нет отдельных SEO-страниц для значения атрибута, но отдельные значения атрибутов с картинками показываться одновременно могут.

4) Товар и варианты:
   - Товар: базовая сущность с привязкой к нескольким категориям, бренду, набору атрибутов, лейблов, статусу публикации и медиа.
   - Варианты: задать модель, в которой часть атрибутов является “вариативными” (например, цвет/размер), другие — описательные; позволить изображения на уровне значения вариативного атрибута. Правила агрегации цены/скидки/остатков: на товар или на вариант.
   - Мини-превью (ultra-light) для списка: предусмотреть отдельное поле/ссылку для сверхлегкой версии главного изображения варианта/товара, чтобы ускорить ленты.

5) Цены и скидки:
   - Цена есть у всех товаров/вариантов (указать уровень).
   - Скидки: поддержать типы “процент” и “абсолютная сумма”; опционально — “цена по карте/спец. цена” и планировщик по времени (start_at/end_at). Указать единицы и приоритеты пересечения скидок и промо-лейблов.
   - В итоговой цене указать расчет, правила округления и хранение валюты.

6) Лейблы:
   - Общая система лейблов (SALE, NEW, “Черная Пятница”, “Супер цена” и пр.).
   - Правила: авто-условия (например, SALE от X% скидки), ручное назначение, запрет автоназначения для конкретного товара/категории/бренда. Опишите приоритеты и конфликты.
   - Отображение: на карточке и на странице товара; правый/левый угол как из требований UX.

7) Медиа и изображения:
   - Хранение в S3/CDN. В базе — ссылки и метаданные.
   - Поля медиа: обоснуйте необходимость хранения width/height (для предотвращения CLS), mime, bytes (лимиты/алиби для CDN), alt. Для LQIP укажите стратегию: хранить мини-версии либо base64; когда это выгодно; когда достаточно скелетона.
   - Варианты изображений: опишите стратегию генерации нескольких размеров и webp/avif. Зафиксируйте минимальный набор (например, превью и webp), либо храним “variants” JSON — объяснить плюсы/минусы.
   - SiteAsset: отдельная сущность для глобального логотипа/фавиконки/OG-картинки по умолчанию для категорий (и страниц). Указать политику переопределений и fallback.

8) Поиск, фильтрация, сортировка:
   - Поиск по названию товара, бренда, категории, значениям атрибутов: выбрать стратегию Postgres FTS, trigram, accent-insensitive, транслитерация (RU→EN).
   - Фильтрация по фасетам: обеспечить быстрый расчет доступных значений и их счетчиков в поддереве категории.
   - Сортировки: по цене, новизне, популярности, скидке, рейтингу; указать индексы/материализованные поля/кеши.
   - Пагинация: курсорная, стабильные сортировки; лимиты по размеру страницы.
   - Сложность: сформулировать Big-O для запросов категории с фильтрами и фасетами.

9) Инвентарь, корзина, избранное, заказы, доставка:
   - Остатки: на уровне варианта; резервы при оформлении; защита от oversell (оптимистические/пессимистические стратегии).
   - Избранное: операция toggle должна быть O(1), индексы на user_id+product_id.
   - Корзина: идемпотентность операций добавления/изменения количества; гостевая корзина (cookie/local) с последующей привязкой к пользователю.
   - Заказы: статусы, оплата (провайдер будет выбран позже), отмены/возвраты, чеки/фискализация (как опциональная перспектива).
   - Доставка: адресная книга пользователя, слоты времени, “примерка без предоплаты” — модель заказа/резерва и SLA по истечению слота.
   - Логи и аудит изменений по заказам.

10) Отзывы, рейтинги, вопросы:
   - Модель отзывов и Q&A: модерация, рейтинг, агрегация среднего рейтинга и количества отзывов; защита от спама; индексы.

11) Производительность и кеширование:
   - Стратегии кеша: на уровне Postgres (материализованные представления/денормализованные таблицы), на уровне приложения (in-memory), на уровне CDN (статические и ISR/SSG для категорий/товаров/брендов).
   - Next.js: указать где SSR/ISR/RSC/streaming целесообразны; lazy-loading для баннеров; приоритеты загрузки изображений.
   - Целевые показатели: TTFB/TTI для главной/категории/товара, бюджет по весу страницы и изображениям.

12) Миграции, импорт, устойчивость:
   - Drizzle миграции, стратегии откатов, миграции без простоя.
   - Импорт каталога (CSV/Excel) и массовые обновления (цены/остатки/атрибуты).
   - Резервное копирование, восстановление, мониторинг, алерты.

13) Безопасность и соответствие:
   - Управление доступами: роли USER/ADMIN/MANAGER с детальными правами (например, MANAGER: товары/заказы, ADMIN: все, включая системные настройки).
   - Защита PII, хранение токенов, логирование доступов, шифрование на канале, подписанные URL для загрузки в S3.
   - Политики сроков хранения логов и данных, GDPR-практики (удаление/экспорт данных пользователя).

14) Конвенции и метаданные:
   - Идентификаторы (например, ULID/UUID), created_at/updated_at везде, soft delete где нужно (и индексы учитывают только не удаленные).
   - Поля для сортировки меню (sort_order): обосновать необходимость или предложить альтернативу.
   - Транслитерация slug: правила для RU→EN, уникальность в пределах родителя и глобальная уникальность full_path.
   - Часовые пояса/валюта/налоги: зафиксировать допущения и расширяемость на будущее.
