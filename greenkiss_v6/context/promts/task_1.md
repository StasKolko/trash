# Архитектурная спецификация Green Kiss

## 0. Общая концепция

Green Kiss — высокопроизводительный интернет‑магазин одежды на Next.js 16 (App Router, RSC, Server Actions) + Postgres + Drizzle ORM, с готовой аутентификацией (NextAuth v5) и инфраструктурой (Bun, Docker, Traefik, CI/CD, S3).

Архитектура строится вокруг:

- Чёткой предметной модели: категории, бренды, атрибуты, товары/варианты, цены, остатки, заказы, доставка, отзывы, медиа.
- Индексной витрины (`product_variant_index`) для быстрых листингов/поиска/фасетов.
- Разделения прав ролей USER / MANAGER / ADMIN.
- Server Actions как основного слоя API в рамках Next.js App Router.
- Admin‑панели поверх этих действий.
- Жёсткой формализации бизнес‑правил и предсказуемой сложности операций.

Уже реализованные фрагменты (дерево категорий, бренды, витрина, auth, S3‑обёртка, CI/CD) используются как фундамент и сохраняются.

## 1. Предметная модель

### 1.1. Категории

#### 1.1.1. Сущность Category

Назначение: иерархическая навигация по каталогу (дерево любой глубины), основа для SEO‑структуры и фильтрации.

Обязательные поля (концептуально):

- `id` (строка, глобальный уникальный идентификатор).
- `name` (строка RU, отображаемое название).
- `slug` (строка EN, транслитерация `name`; уникальна в пределах `parent_id`).
- `full_path` (строка, конкатенация slug’ов по дереву, уникальна глобально).
- `parent_id` (nullable, ссылка на родительскую категорию).
- `status` (enum: `draft` | `active` | `hidden`).
- `sort_order` (целое, ручной порядок в меню).
- `level` (целое, глубина в дереве, 0 — корень).
- `description` (строка, опционально, до ~2000 символов; используется для SEO‑текста и контента на странице категории).
- `created_at`, `updated_at`.
- `deleted_at` (soft delete).

SEO‑поля:

- `meta_title` (строка, по умолчанию = `name`, можно задавать вручную).
- `meta_description` (строка, рекомендуется заполнять, до ~300 символов).
- `og_title` (строка, по умолчанию = `name`).
- `og_description` (строка, рекомендуется заполнять, до ~300 символов).
- `og_type` (строка, по умолчанию `website`).
- `meta_robots` (строка, по умолчанию `index,follow`, можно менять на `noindex,nofollow` для служебных категорий).
- `canonical_url` (строка, URL = `https://greenkiss.ru/` + `full_path`; можно переопределить для канонизации).

Изображения:

- По умолчанию OG‑картинка не хранится в категории.
- Категория использует OG‑изображение по умолчанию из `SiteAsset` (см. ниже).
- Опциональное поле `og_image_asset_id` (nullable) может быть введено для переопределения OG‑картинки для важных категорий (коллекции, спец‑проекты). Рекомендуется заложить это поле: оно не увеличивает сложность, но даёт гибкость SEO/маркетингу.

Связи и индексы:

- FK `parent_id` → `Category.id`, on delete: `SET NULL`.
- Уникальный индекс `(parent_id, slug)` для обеспечения уникальности slug среди «братьев».
- Уникальный индекс `full_path` для быстрого роутинга по URL.

Сложности:

- CRUD одной категории: O(1) по данным Category + O(h) по дереву (через closure).
- Поиск категории по `full_path`: O(log N) по B‑tree индексу.

#### 1.1.2. Сущность CategoryClosure (closure table)

Назначение: хранение всех пар (ancestor, descendant) для дерева категорий, ускорение операций с деревом.

Поля:

- `ancestor_id` (FK → Category.id, not null).
- `descendant_id` (FK → Category.id, not null).
- `depth` (целое, 0 — сама категория, 1 — непосредственный потомок, далее по глубине).

Ключи и индексы:

- PK (`ancestor_id`, `descendant_id`).
- Индекс по `ancestor_id` для выборки поддерева (все потомки предка).
- Индекс по `descendant_id` для выборки пути вверх (все предки узла).

Почему closure table лучше adjacency list:

- Хлебные крошки:
  - adjacency: требуется рекурсивный запрос; O(h) с рекурсией.
  - closure: один запрос по `descendant_id = current` с сортировкой по `depth`; O(h) по результату, без рекурсии.
- Фильтрация по поддеревьям:
  - adjacency: нужен рекурсивный CTE; сложнее кешировать и индексировать, сложность ~O(k) + накладные на рекурсию.
  - closure: один запрос по `ancestor_id = categoryId` → список `descendant_id`; O(k) где k — размер поддерева, без рекурсии.
- Агрегации (количество товаров/брендов):
  - closure: можно использовать `category_closure` при подсчёте товаров/брендов по поддереву и поддерживать материализованные счётчики; предсказуемая сложность O(k).
- Стоимость поддержки:
  - вставка категории: необходимо добавить строки для всех предков + саму категорию: O(h), где h — глубина дерева (обычно малая: 3–5).
  - обновление родителя: требуется пересчитать closure для поддерева — операция редкая, может выполняться батчем.

Сложности:

- Вставка/обновление категории: O(h).
- Построение хлебных крошек: O(h).
- Выбор поддерева: O(k), k — количество узлов в поддереве.

### 1.2. Бренды

#### 1.2.1. Сущность Brand

Назначение: бренд одежды, используется в фильтрах, на картах товаров, на PDP.

Поля:

- `id` (строка).
- `name` (строка, уникальна без учёта регистра, любой язык).
- `image_asset_id` (nullable, FK → MediaAsset, иконка 32×32 webp).
- `created_at`, `updated_at`, `deleted_at` (soft delete).

Уникальность имени:

- Логическая уникальность: name в нижнем регистре уникален (можно обеспечить индексом на выражение LOWER(name)).
- Это позволяет избежать дубликатов «Nike»/«NIKE»/«nike».

SEO для брендов:

- Для MVP не создаём отдельные SEO‑страницы/поля на бренды:
  - Контентный объём велик, поддерживать meta/OG по каждому бренду дорого.
  - Основной трафик и SEO‑работа сосредоточена на категориях, коллекциях и отдельных PDP.
  - Брендовые страницы можно добавить на следующем этапе, если бизнес решит, что это нужно.

Индексы:

- Уникальный индекс на `LOWER(name)`.

#### 1.2.2. Материализация связи бренд–категория: brand_category_counts

Назначение: быстрый фильтр брендов внутри категории и подсчёт количества товаров бренда в категории/поддереве.

Поля:

- `brand_id` (FK → Brand.id).
- `category_id` (FK → Category.id).
- `count` (целое, число товаров бренда в этой категории или её поддереве).
- `last_recalc_at` (дата/время последнего пересчёта).

Первичный ключ:

- PK(`brand_id`, `category_id`).

Индексы:

- Индекс по `category_id` (для быстрого получения брендов категории).
- Дополнительный индекс по `brand_id` (аналитика, выбор списков категорий бренда).

Семантика `count`:

- Рекомендуемый вариант: `count` хранит количество товаров бренда во всём поддереве данной категории:
  - тогда на экране категории можно быстро показать бренды, присутствующие в любом её потомке;
  - при добавлении товара в «глубокую» категорию счётчик инкрементируется у всех предков.

Логика обновления:

- При добавлении товара в категорию:
  - определяем все предки категории (через CategoryClosure) + саму категорию (depth >= 0).
  - для каждой пары (brand_id, ancestor_category_id) инкрементируем `count`.
- При удалении товара, отвязке товара от категории или смене бренда:
  - аналогично проходим по всем предкам категории и декрементируем `count` для соответствующего бренда.
  - если `count` достигает 0 — удаляем строку (`brand_id`, `category_id`).

Сложность:

- Одно изменение «товар ↔ категория»:
  - требуется получить предков категории: O(h).
  - обновить h записей в brand_category_counts: O(h).
- Важная деталь: при удалении дочерней категории или товара:

  - мы уменьшаем `count` только для тех пар (`brand_id`, `ancestor_id`), которые связаны с этим товаром.
  - если у родителя есть другие товары этого бренда (из других дочерних категорий), их записи в brand_category_counts останутся с положительным `count`, поэтому связь не «отвалится».

  Это гарантируется тем, что `count` — агрегированный счётчик по всем товарам бренда для данной категории/поддерева.

### 1.3. Атрибуты, характеристики и фильтры

#### 1.3.1. Модель атрибутов

Назначение: описывать и фильтровать товары (цвет, размер, сезон, материал и пр.), плюс формировать вариативность (варианты).

Основные сущности:

1. **Attribute**

   Поля:

   - `id`.
   - `code` (внутренний код/slug атрибута; уникален).
   - `name` (человекочитаемое название, RU).
   - `type` (enum: `string`, `enum`, `number`, `range`, `boolean`, `multi_select`).
   - `is_variational` (bool; если true — участвует в формировании вариантов товара).
   - `has_images` (bool; если true — значения атрибута могут иметь до 5 изображений и влиять на визуализацию варианта).
   - `unit` (опционально, строка, единица измерения, например «см», «%»).
   - `created_at`, `updated_at`, `deleted_at`.

2. **AttributeValue**

   Поля:

   - `id`.
   - `attribute_id` (FK → Attribute).
   - `value_normalized` (строка или число в нормализованном виде — для индексов; например, `'red'`, `'xl'`).
   - `label` (строка, отображаемое значение, напр. «Красный»).
   - Дополнительные поля:
     - `color_hex` (строка, опционально — для цвета).
   - Связь с медиа:
     - M:N на `MediaAsset`, но ограничением «до 5 картинок» логикой уровня приложения. Можно сделать промежуточную таблицу `attribute_value_media` с сортировкой.
   - `created_at`, `updated_at`, `deleted_at`.

   Уникальность:

   - Уникальный индекс (`attribute_id`, `value_normalized`) для избежания дубликатов.

3. **AttributeValueMedia (опциональная сущность при расширении)**

   - `id`.
   - `attribute_value_id` (FK).
   - `media_asset_id` (FK).
   - `position` (порядок в галерее атрибутного значения).

#### 1.3.2. Привязка атрибутов к категориям

Сущность: `CategoryAttribute`

Назначение: описание того, какие атрибуты применимы в данной категории и как они наследуются.

Поля:

- `id`.
- `category_id` (FK → Category).
- `attribute_id` (FK → Attribute).
- `required` (bool; обязательно ли указывать на товаре/варианте).
- `visibility` (enum: `listing`, `pdp`, `both`, `hidden`).
- `filterable` (bool; используется ли атрибут в фильтрах/фасетах).
- `inheritance_mode` (enum: `to_descendants`, `local_only`):
  - `to_descendants` (по умолчанию): атрибут применяется ко всем потомкам категории.
  - `local_only`: атрибут применяется только к самой категории (редкий кейс).
- `sort_order`.

Расчёт итогового набора атрибутов для товара:

1. Товар принадлежит одной или нескольким категориям.
2. Для каждой категории:
   - собирам все `CategoryAttribute`, объявленные в этой категории.
   - по дереву вверх (через CategoryClosure, предки) добавляем все атрибуты с `inheritance_mode = to_descendants`.
3. Итоговый список атрибутов товара — объединение по всем связанным категориям, с разрешением конфликтов:
   - если один и тот же атрибут встречается несколько раз с разными настройками (например, `visibility` или `required`), берём наиболее специфичные (ниже по дереву) настройки или приоритет `required = true`/`filterable = true`, `visibility` = максимум видимости (`both` > `pdp` > `listing` > `hidden`).

Пример с удалением категории:

- Есть дерево: Одежда → Брюки → Легинсы.
- Атрибут «материал» привязан к «Легинсы» с `to_descendants`.
- Категория «Легинсы» удаляется (soft delete + удаление связей CategoryAttribute только для неё).
- Родитель «Брюки» и другие потомки сохраняют свои CategoryAttribute; товары, которые были только в «Легинсы», при переводе в другие категории должны быть перепривязаны вручную через админку.
- Важно: удаление категории не удаляет сам атрибут «материал» и не затрагивает CategoryAttribute других веток; существующие товары в других категориях, где «материал» был доступен по наследованию от других предков, продолжают его иметь.

Заключение: атрибут — глобальная сущность, привязка к категории — локальная и может быть удалена без воздействия на другие ветки, если продукты перепривязаны.

#### 1.3.3. Значения атрибутов на товаре/варианте

1. **ProductAttributeValue**

   - Назначение: описательные характеристики товара (на уровне продукта).
   - Поля:
     - `id`.
     - `product_id` (FK).
     - `attribute_id` (FK, `is_variational = false`).
     - `attribute_value_id` (FK → AttributeValue либо «свободный текст/число» в зависимости от типа).
     - `value_string`, `value_number`, `value_boolean` (в зависимости от типа).
   - Уникальность:
     - один атрибут не должен дублироваться на товаре: уникальный индекс (`product_id`, `attribute_id`).

2. **VariantAttributeValue**

   - Назначение: вариативные признаки (цвет, размер и т.п.) на уровне варианта.
   - Поля:
     - `id`.
     - `variant_id` (FK → ProductVariant).
     - `attribute_id` (FK, `is_variational = true`).
     - `attribute_value_id` (FK).
   - Уникальность:
     - Набор `attribute_value_id` для варианта должен быть уникален внутри продукта:
       - можно реализовать через технический «fingerprint» (строка с отсортированным списком id) и уникальный индекс (`product_id`, `fingerprint`).

3. Логика отображения вариативных атрибутов (к примеру, цвет):

   - Если для значений атрибута (например, цвет) определены изображения (через `AttributeValueMedia`):
     - В листинге товар может показываться по «цветовым карточкам» (каждый цвет — свой image, своя карта).
     - В PDP галерея/карусель меняется в зависимости от выбранного значения.
   - Если для значений нет изображений:
     - В листинге показывается aggregated view продукта (по дефолтному варианту), цвета/размеры — как бейджи, а не отдельные карточки.

Важно: SEO‑страниц на уровне отдельных значений атрибутов не создаём (по умолчанию). Они участвуют только в фильтрации и поиске.

### 1.4. Медиа и SiteAsset

#### 1.4.1. Сущность MediaAsset

Назначение: единая точка хранения метаданных для файлов (изображения, видео и т.п.), загруженных в S3/CDN.

Поля:

- `id`.
- `bucket` (строка, имя бакета).
- `key` (строка, путь в бакете).
- `url` (строка, полный CDN URL для быстрой отдачи; кэшируемый).
- `width`, `height` (целые, пиксели).
- `bytes` (целое, размер файла).
- `mime` (строка, MIME‑тип).
- `alt` (строка, альтернативный текст для SEO/доступности).
- `lqip` (строка или JSON, мини‑превью: base64 или blurhash, опционально).
- `variants` (JSON‑структура: описание генераций — разные размеры, webp/avif, кропы).
- `created_at`, `deleted_at`.

Обоснования:

- `width`/`height`:
  - нужны для избежания CLS, чтобы сразу зарезервировать место под изображение.
  - позволяют делать aspect‑ratio и responsive layout без скачков.
- `mime` и `bytes`:
  - валидация при загрузке (ограничения по типу и размеру).
  - аналитика и потенциальные ограничения (например, не грузить >5МБ).
- `lqip`:
  - не обязателен для всех типов медиа.
  - обязательно нужен для карточек товаров, основного PDP и важных баннеров.
  - формат:
    - base64‑миниатюра (маленький PNG/WebP) — простая интеграция с `<Image/>`, но чуть тяжелее по размеру.
    - blurhash — компактнее, но требует декодера на клиенте.
  - Рекомендуется blurhash или очень маленький base64‑jpeg, хранить только там, где реально используется (товары, баннеры, OG). Поле `lqip` можно оставить nullable.
- `variants` (JSON):
  - позволяет гибко описывать набор деривативов (например, `{ "thumbnail": { "w": 200, "h": 300, "url": "..." }, "webp_1x": {...}, "webp_2x": {...} }`).
  - лучше, чем «магические» поля `webp_url`, `thumb_url`, потому что:
    - масштабируется при добавлении новых форматов/размеров.
    - удобен для клиентских стратегий выбора источника (по DPR/ширине).

Индексы:

- По `key` (уникальный).
- По `created_at` (удобно для медиа‑менеджера в админке).

#### 1.4.2. Сущность SiteAsset

Назначение: глобальные ассеты сайта (логотипы, OG‑картинки по умолчанию, фавиконки и пр.).

Поля:

- `id`.
- `type` (enum: `logo_main`, `logo_dark`, `favicon`, `og_default`, `category_default_image`, `homepage_hero` и т.п.).
- `media_asset_id` (FK → MediaAsset).
- `active` (bool).
- `created_at`, `updated_at`.

Модель выбора активного ассета:

- Для каждого `type` может быть несколько записей, но только одна `active = true`.
- При выборе (например, `og_default`) в запросе берём `WHERE type = 'og_default' AND active = true ORDER BY created_at DESC LIMIT 1`.

Использование категориями и страницами:

- Категория:
  - Если `og_image_asset_id` не задано:
    - использует `SiteAsset(type = 'og_default')`.
  - Если задано — использует его.
- Товар:
  - PDP использует отдельное медиа из своей галереи или `og_image_asset_id` на продукте.
- Главная страница:
  - Использует `SiteAsset(type = 'homepage_hero')` для баннеров и т.п.

#### 1.4.3. Связи медиа с доменной моделью

1. **Товар (Product)**:

   - Галерея: M:N таблица `product_media`:
     - `product_id`, `media_asset_id`, `position`, `is_main`, `is_og`.

### 1.5. Товары, варианты, цены, скидки, лейблы, остатки

#### 1.5.1. Product

Назначение: логическая сущность товара (PDP), объединяющая варианты.

Поля:

- `id`.
- `brand_id` (nullable FK → Brand).
- `name` (строка).
- `slug` (строка, уникальна в пределах сайта или по комбинации с id; используется для URL PDP).
- `status` (enum: `draft` | `active` | `hidden` | `archived`).
- `published_at` (дата/время).
- SEO‑поля:
  - `meta_title`, `meta_description`, `og_title`, `og_description`, `og_type` (`product`), `meta_robots`, `canonical_url`.
- `created_at`, `updated_at`, `deleted_at`.

Связи:

- M:N с Category через `product_category`:
  - `product_id`, `category_id`, `is_primary`.
  - `is_primary = true` — основная категория PDP (для хлебных крошек и canonical URL).
- M:N c Label (см. ниже).
- 1:N с ProductVariant.

Индексы:

- PK по `id`.
- Уникальный индекс по `slug` (либо по `(slug, brand_id)` — бизнес‑решение).
- Индекс по `status` и `deleted_at` для фильтрации активных.

#### 1.5.2. ProductVariant

Назначение: минимальная продаваемая единица (SKU).

Поля:

- `id`.
- `product_id` (FK).
- `sku` (строка, уникальная).
- `barcode` (опционально).
- `is_default` (bool; один вариант на продукт).
- `active` (bool).
- Физические характеристики:
  - `weight_grams`, `volume_cm3` (для доставки).
- Даты:
  - `created_at`, `updated_at`, `deleted_at`.
- `ultra_light_asset_id` (nullable FK → MediaAsset) — ссылка на суперлёгкую мини‑картинку для листинга (опционально; может быть вычислена из галереи).

Связи:

- 1:N → VariantAttributeValue.
- 1:1 → Inventory (по variant_id).

Индексы:

- Уникальный индекс по `sku`.
- Индекс по (`product_id`, `is_default`).

#### 1.5.3. Цены и скидки

Модель:

- Историчность на уровне варианта.
- Обновляемый слой «активной» цены для быстрых чтений.

Сущности:

1. **Price**

   Поля:

   - `id`.
   - `variant_id` (FK).
   - `base_price_cents` (целое).
   - `discount_type` (enum: `none`, `percent`, `fixed`, `special`).
   - `discount_value` (для % — число с точностью до сотых, для fixed — целое в центах).
   - `valid_from`, `valid_to` (временной интервал действия; `valid_to` может быть null).
   - Метаданные (источник: промо‑акция, ручная правка, импорт).
   - `created_at`.

   Назначение:

   - Историческое хранение всех изменений цен.

2. **EffectivePrice**

   Поля:

   - `variant_id` (PK + FK).
   - `price_cents_effective` (текущая цена).
   - `compared_at_price_cents` (старая цена для отображения зачёркнутого значения).
   - `discount_percent` (число).
   - `updated_at`.

   Назначение:

   - Предвычисленный слой для чтения в листингах и PDP.
   - Обновляется по триггеру/фоновому джобу при изменении Price.

Приоритеты скидок:

- Если одновременно действуют несколько правил:
  - `special` (карточная/персональная цена) имеет наивысший приоритет и полностью определяет цену.
  - Далее применятся другие правила в фиксированном порядке:
    1. фиксированная скидка (fixed),
    2. процентная (percent),
  - Допускается только одно активное правило каждого типа; разрешение конфликтов:
    - более позднее по времени создания/последнему изменению (LWW) либо с более высоким приоритетным полем.
- Округление:
  - Применить банковское округление до целого числа рублей (центов).
  - Отображаемый процент скидки округлять до целого вверх (например, 24.1% → 25%).

#### 1.5.4. Лейблы

Назначение: бейджи вида SALE, NEW, «Чёрная пятница», «Хит», используемые в UI.

1. **Label**

   Поля:

   - `id`.
   - `code` (строка, уникальный идентификатор, напр. `sale`, `new`, `black_friday`).
   - `name` (строка, отображаемое имя).
   - `position` (enum: `top_left`, `top_right`, `bottom_left`, `bottom_right`, `both_top`, ...).
   - `priority` (целое; чем выше — тем более приоритетный, влияет на конфликтующие лейблы).
   - `bg_color`, `text_color` (строки, HEX/имена Tailwind).
   - `created_at`, `updated_at`.

2. **LabelAssignment**

   Поля:

   - `label_id` (FK).
   - `product_id` (либо `variant_id`, если лейбл специфичен для варианта).
   - `manual` (bool; ручное назначение или авто).
   - `created_at`.

3. **LabelAutoRule**

   Поля:

   - `id`.
   - `label_id` (FK).
   - Условие применения (концептуально):
     - `min_discount_percent` (товар имеет скидку ≥ X%),
     - `max_days_since_published` (товар новее N дней),
     - `promo_code` или `campaign_id` (для специальных акций).
   - `active` (bool).
   - `priority` (для порядка применения правил, доп. к приоритету лейбла).

4. **LabelBlocklist**

   Поля:

   - `id`.
   - `label_id` (FK).
   - `scope_type` (enum: `product`, `category`, `brand`).
   - `scope_id` (id соответствующей сущности).
   - Назначение: явно запрещает навешивание данного лейбла авто‑правилами на этот продукт/категорию/бренд.

Разрешение конфликтов:

- Для набора доступных лейблов на продукт:
  - Если есть ручные (`manual = true`) и автоматические — ручные всегда имеют приоритет: они не снимаются автоматически.
  - Если на одну и ту же позицию попадает несколько лейблов:
    - выбирается лейбл с максимальным `priority`.
  - Авто‑лейблы не применяются, если в blocklist для этого scope уже есть запись.

Использование:

- `SALE`:
  - Авто‑правило: `min_discount_percent >= X`.
- `NEW`:
  - Авто‑правило: `max_days_since_published <= N`.
- `BLACK_FRIDAY`:
  - Авто‑правило: активная промо‑кампания по времени и флаг продуктового участия.

#### 1.5.5. Inventory и остатки

Назначение: учёт реальных остатков и предотвращение oversell.

Сущности:

1. **Inventory**

   Поля:

   - `variant_id` (PK + FK).
   - `on_hand` (целое, общее количество на складе).
   - `reserved` (целое, зарезервировано под незавершённые/не отправленные заказы).
   - `available` (вычисляемое или явно хранимое поле = `on_hand - reserved`).
   - `updated_at`.

2. **InventoryLedger**

   Поля:

   - `id`.
   - `variant_id`.
   - `delta_on_hand` (целое, может быть отрицательным).
   - `delta_reserved`.
   - `reason` (enum: `purchase`, `order_reserve`, `order_release`, `manual_adjustment`, `return`).
   - `order_id` (nullable), `comment`.
   - `created_at`, `created_by` (FK → User).

Стратегия защиты от oversell:

- Рекомендуемый вариант — пессимистическая блокировка в пределах одной транзакции:

  1. При резерве (в процессе checkout):
     - Начинаем транзакцию.
     - Читаем строку Inventory для варианта `FOR UPDATE`.
     - Проверяем, что `on_hand - reserved >= qty_requested`.
     - Если да:
       - увеличиваем `reserved` на `qty_requested`.
       - создаём запись в InventoryLedger.
     - Если нет:
       - откатываем транзакцию, бросаем ошибку (недостаточно остатков).
  2. При подтверждении оплаты/отправке:
     - В транзакции:
       - уменьшаем `on_hand` на qty, уменьшаем `reserved` на qty (или только `reserved` → 0 если модель другая).
  3. При отмене заказа/истечении резерва:
     - `reserved` уменьшается на qty, `on_hand` остаётся прежним.

Сложность операций:

- Резерв/списание: O(1) на вариант + O(1) на запись в Ledger (при условии индекса по `variant_id`).

### 1.6. Индексная витрина и поиск

#### 1.6.1. Сущность product_variant_index

Назначение: плоская материализованная витрина для быстрых запросов листингов, фильтров и поиска.

Строка = 1 вариант.

Поля:

- Идентификаторы и флаги:

  - `variant_id`.
  - `product_id`.
  - `brand_id`.
  - `active_product` (bool).
  - `active_variant` (bool).

- Категории и атрибуты:

  - `category_ids` (массив всех категорий продукта, включая всех предков через CategoryClosure).
  - `primary_category_id`.
  - `attr_value_ids` (массив всех значений атрибутов варианта + важные описательные атрибуты на уровне продукта, используемые в фильтрах).

- Цены, остатки, реакции:

  - `price_cents_effective`.
  - `discount_percent`.
  - `has_stock` (bool; `available > 0`).
  - `rating_avg` (float).
  - `rating_count` (int).
  - `popularity` (float или int, комбинация продаж/просмотров/кликов).
  - `created_at_product`.
  - `created_at_variant`.

- Поиск:

  - `searchable_tsv` (tsvector, включает:
    - имя товара,
    - бренд,
    - важные атрибуты (цвет, размер, материал),
    - возможно, названия категорий).

Индексы:

- GIN индекс по `category_ids` (для `category_ids @> ARRAY[catId]`/`catId = ANY(category_ids)`).
- GIN индекс по `attr_value_ids` (фильтрация по значениям атрибутов).
- GIN индекс по `searchable_tsv` (FTS).
- BTree индексы:
  - по `price_cents_effective` (для сортировки по цене).
  - по `created_at_product`/`created_at_variant` (для сортировки по новизне).
  - по `popularity`.

Пересчёт:

- Обновление индекса должно происходить при изменении:

  - статуса продукта/варианта,
  - цен (`EffectivePrice`),
  - остатков (Inventory, флаг `has_stock`),
  - атрибутов,
  - привязок к категориям,
  - бренда,
  - агрегатов отзывов (rating_avg/rating_count).

- Технически:
  - через триггеры в БД (для простых случаев: изменение цен/остатков) + фоновый воркер (Cron/job queue) для тяжёлых пересчётов (переезд товара между категориями с большим поддеревом).
- SLA: обновление записи в `product_variant_index` в течение ≤ 30 секунд после изменения «источника правды».

Сложности:

- Обновление одной строки индекса: O(1).
- Пересчёт по продукту (несколько вариантов): O(V), где V — количество вариантов.
- Случаи массовых изменений обрабатываются батчами.

#### 1.6.2. Поиск

Модель:

- Основной текстовый поиск: Postgres FTS (tsvector/tsquery).
- Автодополнение и устойчивость к опечаткам/транслитерации: `pg_trgm` + `unaccent` + кастомная функция транслитерации RU→EN (или наоборот).

Индексы:

- `searchable_tsv` — GIN индекс.
- Для trigram‑поиска:
  - GIN/GiST индекс по `name` брендов и категорий (для автодополнения).
- При вставке/обновлении:
  - формируем `searchable_tsv` из:
    - product.name,
    - brand.name,
    - категорий,
    - значимых атрибутов.

Транслитерация:

- На запись:
  - можно создавать дополнительные поля (`searchable_name_translit`), подготовленные из RU → EN.
- На запрос:
  - входная строка нормализуется:
    - lower case,
    - удаление диакритики (`unaccent`),
    - транслитерация (чтобы `platya` находило «платья»).

#### 1.6.3. Фильтрация и фасеты

Запрос листинга:

- Фильтры:

  - по `category_ids`:
    - выбрав категорию в UI, фактически фильтруем по `category_ids` = ANY(выбранных id) — это уже включает поддерево благодаря материализации в индексе.
  - по `attr_value_ids`:
    - фильтруем по `attr_value_ids` с GIN‑индексом.
  - по диапазону цены:
    - используем BTree индекс по цене.
  - `has_stock`:
    - фильтр по bool.

- Сортировки:

  - по новизне: `ORDER BY created_at_product DESC` или `created_at_variant DESC`.
  - по цене: `ORDER BY price_cents_effective ASC|DESC`.
  - по популярности.

Фасеты:

- Вычисляются как агрегаты по уже отфильтрованному подмножеству:

  1. Строится основной запрос base (фильтры категории, цены, наличия).
  2. Для фасета по бренду:
     - `SELECT brand_id, COUNT(*) FROM product_variant_index WHERE base_conditions GROUP BY brand_id`.
  3. Для фасетов по атрибутам:
     - либо:
       - джойним список возможных атрибутных значений к индексу и считаем `COUNT(DISTINCT product_id)`/`COUNT(*)`.
     - либо:
       - выполняем запрос вида: `SELECT attr_value_id, COUNT(*) FROM product_variant_index, UNNEST(attr_value_ids) AS attr_value_id WHERE base_conditions GROUP BY attr_value_id` (если размер результата разумный).

Кеширование фасетов:

- Ключ кэша:
  - зависит от:
    - набора фильтров (category, price range, attr_value_ids),
    - сортировки (на фасеты влияет только фильтрация, не сортировка; можно сортировку не учитывать),
    - страницы (на фасеты, как правило, не влияет номер страницы).
- Формат:
  - Redis или in‑memory (node) с TTL ~30–120 сек.
- Это сильно уменьшит нагрузку при популярных фильтрациях (особенно на уровне категорий).

Big‑O:

- Запрос списка товаров:
  - при наличии индексов — O(log N + P), где P — количество возвращённых вариантов (до `pageSize`).
- Расчёт фасетов:
  - O(F log N + A), где F — количество фасетных полей, A — суммарное количество возвращённых значений фасетов (обычно умеренное).

## 2. Личный кабинет, корзина, избранное, заказы, доставка

### 2.1. Wishlist (избранное)

Сущность: `WishlistItem`.

Поля:

- `user_id` (FK → User).
- `product_id` (FK → Product).
- `created_at`.

PK/уникальность:

- Уникальный ключ (`user_id`, `product_id`).

Операции:

- Toggle:
  - Проверить, есть ли запись:
    - если есть → удалить.
    - если нет → вставить.
- O(1) по индексу `user_id, product_id`.

### 2.2. Корзина (Cart / CartItem)

Сущности:

1. **Cart**

   Поля:

   - `id`.
   - `user_id` (nullable FK; если пользователь авторизован).
   - `guest_token` (nullable, строка; если гость, хранится в cookie).
   - `created_at`, `updated_at`.

   Уникальные ограничения:

   - Либо `(user_id IS NOT NULL AND guest_token IS NULL)`, либо наоборот.
   - Можно принудительно иметь одну активную корзину на пользователя и на гостя.

2. **CartItem**

   Поля:

   - `id`.
   - `cart_id` (FK).
   - `variant_id` (FK → ProductVariant).
   - `qty` (целое > 0).
   - `price_cents_snapshot` (фиксация цены на момент добавления; используется, если цена изменится до оформления).
   - `created_at`, `updated_at`.

3. **IdempotentOperation**

   (для операций с корзиной и заказами)

   Поля:

   - `idempotency_key` (строка, уникальный).
   - `scope` (строка: `cart_update`, `checkout`, `payment_callback` и т.п.).
   - `created_at`.
   - `response_payload` (JSON, результат операции).
   - `status` (enum: `in_progress`, `completed`, `failed`).

Механика идемпотентности:

- При изменении корзины клиент отправляет заголовок/поле `Idempotency-Key`.
- На сервере:
  1. Ищем запись по (`scope`, `idempotency_key`).
  2. Если есть и `status = completed` — возвращаем сохранённый `response_payload`.
  3. Если нет — создаём запись `in_progress`, выполняем операцию изменения корзины в транзакции, сохраняем результат в `response_payload`, ставим `completed`.

Индексы:

- Уникальный индекс по (`scope`, `idempotency_key`).
- Индекс по `cart_id` на CartItem.

Сложность:

- Добавление/изменение одного CartItem: O(1).

### 2.3. Заказы (Orders / OrderItems)

Сущности:

1. **Order**

   Поля:

   - `id`.
   - `user_id` (nullable).
   - `cart_id` (nullable, связь с исходной корзиной).
   - `status` (enum: `created`, `confirmed`, `paid`, `shipped`, `delivered`, `cancelled`, `returned`).
   - `total_price_cents` (итоговая сумма).
   - `currency` (`RUB`).
   - `address_id` (FK → Address).
   - `delivery_slot_id` (FK → DeliverySlot).
   - `try_on` (bool; режим примерки на дом).
   - `payment_status` (enum: `pending`, `authorized`, `captured`, `failed`, `refunded`).
   - `external_payment_id` (nullable, идентификатор в платёжном провайдере).
   - `created_at`, `updated_at`.

2. **OrderItem**

   Поля:

   - `id`.
   - `order_id` (FK).
   - `variant_id` (FK → ProductVariant).
   - `qty`.
   - `price_cents` (за единицу).
   - `discount_cents` (на единицу).
   - `total_cents` (итог по строке).
   - Снепшоты полей продукта (название, бренд, размер, цвет) для правильного отображения даже при изменениях каталога.

Связь с Inventory/Reservation:

- На шаге `confirmed` (подтверждение заказа после checkout, до оплаты или одновременно):

  - создаём резервы в Inventory (см. выше) для каждого OrderItem.
  - для режима `try_on` (примерка без предоплаты) резервируется:
    - товар,
    - слот доставки (см. далее).

- Резерв истекает:
  - по таймеру (например, через 30–60 минут без оплаты) — для обычных заказов.
  - по отдельной бизнес‑логике — для примерки (может быть дольше, но фиксировано).

### 2.4. Доставка: DeliverySlot / Address / Reservation

1. **Address**

   Поля:

   - `id`.
   - `user_id`.
   - `country`, `city`, `street`, `house`, `apartment`, `postal_code`, `comment`.
   - `is_default`.
   - `created_at`, `updated_at`.

2. **DeliverySlot**

   Поля:

   - `id`.
   - `date` (дата).
   - `time_from`, `time_to` (интервалы).
   - `capacity` (максимальное количество заказов/условная «ёмкость»).
   - `reserved` (текущее количество резервов).
   - `try_on_allowed` (bool).
   - `created_at`, `updated_at`.

3. **DeliveryReservation**

   Поля:

   - `id`.
   - `order_id`.
   - `delivery_slot_id`.
   - `reserved_at`.
   - `expires_at` (опционально; зависит от политики).
   - `try_on` (bool).

Модель:

- При выборе слота в checkout:
  - проверяем, что `reserved < capacity` (в транзакции/с блокировкой на строку слота).
  - инкрементируем `reserved`.
  - создаём запись `DeliveryReservation`.
- При отмене заказа:
  - `reserved` уменьшается.
- Для try‑on:
  - возможно более жёсткие лимиты (меньший capacity), либо отдельные `DeliverySlot` с типом `try_on`.

## 4. Доступы, безопасность, валидация, ошибки

### 4.1. Роли и права

С учётом существующей модели (USER, MANAGER, ADMIN):

- **USER**:

  - Чтение каталога, категорий, брендов, фильтров, поиска.
  - Управление своей корзиной, избранным, адресами.
  - Создание заказов.
  - Создание отзывов/вопросов.
  - Чтение своих заказов и статусов.

- **MANAGER**:

  - Всё, что USER.
  - Управление товарами, вариантами, медиа (кроме системных SiteAsset).
  - Управление ценами, скидками (но в рамках разрешённых правил).
  - Управление остатками (Inventory).
  - Управление заказами (смена статусов, работа с доставкой, примеркой).
  - Модерация отзывов и Q&A.
  - Управление слотами доставки.

- **ADMIN**:

  - Всё, что MANAGER.
  - Управление системными настройками:
    - категории,
    - атрибуты,
    - лейблы и авто‑правила,
    - SiteAsset, SEO глобально,
    - импорт/экспорт,
    - управление пользователями и их ролями,
    - аудит/логирование.

### 4.2. Где и как проверяется доступ

- Слой Server Actions/route handlers:

  - Используем уже реализованные хелперы `requireAdminOrManager`, `requireAdmin` и в дальнейшем `requireUser`.
  - Каждый action по CRUD (каталог, заказы, настройки) начинается с проверки роли.

- Middleware (`proxy.ts`):

  - Уже ограничивает `/admin` для MANAGER/ADMIN.
  - Оставляем как внешний «пояс», но дублируем проверки в Server Actions (как уже делается), чтобы API оставались защищёнными, даже если кто-то обходит UI.

- RSC:

  - Страницы админки — серверные компоненты — также вызывают `requireAdminOrManager` в корневом layout’е и страницах.

### 4.3. Валидация и транзакции

- Валидация входных данных:

  - zod‑схемы для всех входных типов (как уже реализовано для brands и categories).
  - Эти схемы используются как:
    - server‑side в Server Actions,
    - client‑side в формах (через `zodResolver` + react-hook-form).

- Сложные операции (категория + closure, product + brand_category_counts, price + index):

  - Выполняются внутри транзакций (`db.transaction()` в Drizzle):

    - создание/обновление категории:
      - вставка/изменение в Category,
      - обновление CategoryClosure,
      - при необходимости обновление SEO/`canonical_url`.
    - изменение связок product–category–brand:
      - обновление ProductCategories,
      - пересчёт brand_category_counts для всех затронутых предков категорий.
    - изменение цен:
      - вставка Price,
      - обновление EffectivePrice,
      - обновление product_variant_index.

### 4.4. Формат ошибок

Единый формат ответа (для API/Server Actions, который можно поверх обернуть в уже используемый `ApiResponse`):

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": { "...": "..." },
    "requestId": "uuid/trace-id"
  }
}
```

Набор кодов:

- `VALIDATION_ERROR` — неверные параметры запроса.
- `NOT_FOUND` — сущность не найдена.
- `FORBIDDEN` — нет прав (роль не подходит).
- `UNAUTHORIZED` — пользователь не аутентифицирован.
- `CONFLICT` — конфликт состояний (например, конкурентное изменение, idempotency conflict).
- `RATE_LIMITED` — превышен лимит запросов.
- `SERVER_ERROR` — внутренняя ошибка.

Внутри Server Actions можно маппить это на уже существующий `ApiResponse<T>`:

- `success: false`, `error: code`, `details: {...}`.

### 4.5. Безопасность

- CSRF:

  - Для критичных действий, вызываемых из браузера, желательно использовать:
    - встроенную защиту NextAuth для POST к /api/auth/*,
    - либо собственный CSRF‑токен для мультипроектных форм.
  - При Server Actions, привязанных к сессии, риск CSRF ниже, но стоит ограничивать origin/реферер и использовать `SameSite=Lax`/`Strict` для cookie.

- SSRF:

  - Запрещаем произвольные HTTP‑запросы из приложения на внешние URL, кроме строго прописанных (S3, платёжный провайдер и т.п.).
  - Если появляются функции «загрузить по URL», ограничиваем домены/протоколы.

- Загрузка медиа:

  - Ограничиваем типы (white‑list: image/jpeg, image/png, image/webp, image/avif).
  - Ограничиваем размер в байтах (например, до 10МБ).
  - Ограничиваем разрешение в пикселях (например, до 8000×8000).
  - Применяем пост‑обработку (ресайз, конвертация) на бэкенде перед загрузкой в S3.
  - Подписанные URL (pre‑signed) для direct upload с фронта, если потребуется.

- Rate limiting:

  - По IP/пользователю, с использованием Redis/встроенного store:
    - поиск/автодополнение,
    - логин,
    - операции корзины и checkout,
    - отправка отзывов/вопросов.

### 4.6. Аудит

Сущность: `AuditLog`.

Поля:

- `id`.
- `timestamp`.
- `actor_user_id` (nullable; системные события могут быть без пользователя).
- `action` (строка/enum: `CATEGORY_CREATED`, `PRICE_CHANGED`, `INVENTORY_ADJUSTED`, `ORDER_STATUS_CHANGED`, т.д.).
- `entity_type` (строка: `product`, `category`, `order`, `user`, `site_asset`).
- `entity_id`.
- `metadata` (JSON, до/после значения, объяснение причины).

Использование:

- Логируем все важные изменения, особенно:
  - изменения цен,
  - изменения остатков,
  - изменения статусов заказов,
  - изменения ролей пользователей,
  - публикация/архивация товаров/категорий.

### 6.2. Стратегии Next.js и загрузка изображений

- SSR / ISR / RSC / Streaming:

  - Категории и товары:
    - страницы категорий и PDP могут быть SSR с ISR (revalidate 30–300 секунд), чтобы балансировать свежесть и производительность.
  - Главная:
    - ISR с более крупным интервалом (1–5 минут).
  - Админка:
    - force-dynamic (как сейчас) из-за персонализированных данных.

- Изображения:

  - Использовать `<Image>` или оптимизированные `<img>` с:
    - указанием `width`/`height`,
    - `sizes` и `srcset` (используя `variants` из MediaAsset),
    - форматами webp/avif.
  - LQIP:
    - передать `blurDataURL` (если base64) или реализовать blurhash.
  - Приоритет:
    - первый слайд PDP и первые несколько карточек в листинге — более высокий приоритет.
  - Ленивая загрузка:
    - `loading="lazy"` для остальных.

- Учёт существующей инфраструктуры:

  - Healthcheck `/api/health` — уже интегрирован.
  - `ThemeProvider`, `SessionProvider` — уже подключены в RootLayout.

### 6.3. Целевые метрики

- TTFB:

  - главная/категория/PDP ≤ 200–300 ms на сервере (исключая сеть).
- TTI:

  - ≤ 3 секунд на 4G для большинства пользователей.
- CLS:

  - применять width/height к изображениями,
  - избегать отложенного добавления крупных блоков над контентом.

- Ограничения по весу JS:

  - минимизация клиентского JS:
    - вынос логики в Server Components там, где возможно.
    - лесенкой ленивые компоненты (отзывы, Q&A, рекомендации).

- Ограничения по картинкам:

  - не более 1–1.5МБ суммарно на initial viewport (mobile),
  - не более 2–3МБ на desktop initial.

## 7. Миграции, импорт и устойчивость

### 7.1. Миграции (Drizzle)

- Стратегия:

  - Expand/Contract:
    - сначала добавляем новые таблицы/колонки/индексы,
    - затем обновляем код,
    - затем удаляем старые поля.
  - Индексы:
    - создавать CONCURRENTLY (через raw SQL или соответствующие миграции), чтобы не блокировать таблицу.
  - Без простоя:
    - учесть, что миграции запускаются при деплое внутри контейнера (уже настроено).
    - избегать миграций, требующих долгих `ACCESS EXCLUSIVE` блокировок.

### 7.2. Импорт каталога

Поддерживаемые форматы:

- CSV / Excel.

Типы импортов:

- Каталог (товары/варианты/категории/бренды).
- Цены.
- Остатки.
- Атрибуты и значения.

Модель:

- Очередь задач (JobQueue в БД или на внешнем worker):
  - Задача содержит:
    - ссылку на файл в S3,
    - тип импорта,
    - mapping полей.
  - Статусы: `queued`, `processing`, `completed`, `failed`.
- Валидация и откаты:

  - сначала dry run:
    - валидируем строки, считаем потенциальные ошибки.
  - затем реальный run:
    - операции в батчах транзакций (например, по 1000 строк), чтобы избежать огромных транзакций.
  - при ошибках:
    - лог ошибок по строкам, вывод отчёта в админке.

### 7.3. Резервное копирование и мониторинг

- Бэкапы БД:

  - регулярные snapshot’ы базы (через средства Postgres/хостинга).
  - тест восстановления в стейджинге.

- Мониторинг:

  - латентность основных запросов (листинги, PDP, поиск).
  - количество промахов/попаданий кэша (Redis или внутренний).
  - блокировки в БД (особенно при миграциях и массовых операциях).
  - HTTP‑метрики (ответы 5xx, трафик, RPS).

## 8. Сводка решений и открытые вопросы

### 8.1. Сводка ключевых решений

- Категории:
  - Closure table для дерева.
  - `full_path` + уникальный индекс для роутинга.
  - SEO‑поля на уровне Category.
  - `SiteAsset` для OG‑изображений по умолчанию + опциональный override.

- Бренды:
  - Уникальность имени без учёта регистра.
  - brand_category_counts как материализация связи бренд–категория по поддеревьям.
  - Авто‑поддержка через изменения товаров/категорий.

- Атрибуты и варианты:
  - Глобальные Attribute/AttributeValue.
  - CategoryAttribute с наследованием и флагами `required`, `visibility`, `filterable`.
  - Описательные значения на Product, вариативные на Variant.
  - `has_images` на атрибуте для визуальных значений (цвет).

- Цены/скидки/лейблы:
  - Историческая таблица Price + предвычисленный EffectivePrice.
  - Скидки с приоритетами (special > fixed > percent).
  - Label, LabelAutoRule, LabelBlocklist для SALE/NEW/Black Friday.

- Медиа:
  - MediaAsset с `width`, `height`, `mime`, `bytes`, `lqip`, `variants` (JSON).
  - SiteAsset для логотипов/OG по умолчанию/баннеров.

- Поиск и фасеты:
  - product_variant_index как витрина.
  - Postgres FTS + trigram + unaccent + транслитерация.
  - GIN/GiST индексы для массивов и tsvector.
  - Кеширование фасетов.

- Кеширование/ISR/Server Actions:
  - ISR для публичных страниц (главная, категории, PDP).
  - Server Actions для админки/checkout/каталога с персонализацией.
  - Краткоживущий кэш фасетов/автодополнения.

### 8.2. Открытые вопросы (с дефолтами)
